# kraftwerk — agent notes

## "ship"

When asked to **ship** (or "ship to npm", "release"), do the full cycle without asking:

1. Test first, in `kraftwerk/`: `npm run typecheck && npm test && npm run test:e2e && npm run build`. All four must pass (the build is what `prepublishOnly` runs in the publish workflow, and it uses `tsconfig.build.json`, not the typecheck config — a change to either tsconfig can pass the typecheck and still break the publish) before anything is committed; a failing test stops the ship, it is never skipped or deleted to get through. If the change touches a server route, git sync, config loading, or a UI flow, add or extend a test for it (`test/api/` for server behaviour, `e2e/` for browser flows) in the same commit — see the Tests section in `CLAUDE.md` for the layout and fixtures. `e2e/serve.ts` only builds `web/dist` when it is missing, so after a UI change run `npm run build:web` first or the e2e suite tests the previous build.
2. Bump the version in `kraftwerk/package.json` (minor for features, patch for fixes).
3. Commit as `Release X.Y.Z: <summary>` — only the files belonging to the change, leave unrelated working-tree edits (e.g. `agent-playground/`) untouched.
4. Push to `main`.
5. Create the GitHub release: `gh release create vX.Y.Z --target main --title "vX.Y.Z" --notes "..."` — this triggers `.github/workflows/publish.yml` (which runs typecheck and `npm test` again). Never `npm publish` locally.
6. Wait for the workflow to finish: `gh run watch <id> --exit-status`.
7. Install the published version globally: `npm i -g @netnodeag/kraftwerk@X.Y.Z`, then confirm with `kraftwerk --version`.

Running `kraftwerk ui` instances use the global install, so step 7 is what makes the change visible on localhost.

## Tests come with the feature

Any new feature that exposes an API — an inspector route under `/api/`, a CLI command or flag, a `kraftwerk.yml` key — ships with a test in the same commit. No exceptions for "small" endpoints: the test is what proves the contract. Where it goes:

- `kraftwerk/test/api/` — server routes, through the real server on a free port (`startServer` in `test/helpers/project.ts`).
- `kraftwerk/test/cli/` — commands, through the real bin in a fresh process (`cli()` in `test/helpers/cli.ts`).
- `kraftwerk/e2e/` — a browser flow, only when the feature has a screen.

Assert on behaviour a user sees (exit code, JSON shape, a file on disk, a row in the UI), not on internals. Never spawn docker or a coding agent from a test.

The same goes for a workflow contract a playground demo relies on (a file the runner waits for, a step gated with `if:`, an answer the inspector writes): the demo itself cannot be tested (it runs an agent), so the mechanism gets a test with an equivalent script-only workflow driven through the real bin — `test/api/decision-loop.test.ts` is the pattern. A demo dry-run by hand does not count as a test.

## "check tests"

When asked to **check tests** (or "find test gaps", "what is untested"), do not just run the suite. Go through the code and compare it against what the tests cover:

1. List every public surface: `/api/` routes in `src/server/api/` (or `GET /api/protocol`), commands in `src/cli/*.ts`, keys in `src/config.ts`, screens in `web/src/`.
2. For each, find the test that exercises it. Grep `test/` and `e2e/` for the route path, command name, or config key.
3. Report the gaps ranked by risk: writes before reads, security guards before formatting, code paths with error handling before happy paths.
4. Fill the gaps, most important first, then run `npm test` and `npm run test:e2e`. A gap you decide not to fill gets named in the report with the reason.

## Naming

The persistent chat personas are **agents** — in code, routes, CSS, prose and prompts. Not "team", "team member" or "member": `Agent`, `listAgents`, `/api/agents`, chat scope `{ kind: "agent", slug }`, `agents/<slug>/`. "Team" is reserved for the humans using a workspace.

Git clones the agents work on are **repositories** in prose and the UI, `repos` in code, config, routes and the CLI (`ReposConfig`, `listRepos`, `/api/repos`, `kraftwerk repos`, `repos.root`). Not "projects" — that word is the goal-scoped folders under `kraftwerk-data/projects` (see below). The one persisted legacy is chat `meta.json` written before 0.36 with `{ kind: "team", member }`; `store.ts` upgrades it on read, so never write that shape again.

Shared conversations of several agents are **channels** — `channels/<slug>/channel.yml`, `Channel`, `/api/channels`, chat scope `{ kind: "channel", slug }`. The agents in a channel are its **members** (agent slugs); each member holds a **seat** in the chat (`Seat` in `sessions.ts`: one process per member). The one agent of an ordinary chat is the `MAIN` seat. Events in a channel carry `from` (an `Author`: human by name, agent by slug); events in ordinary chats do not.

The workspace's general chat is **Ralv** — the chief of staff and concierge of the workspace: knows everything in it, advises, and helps launch projects, agents, workflows and knowledge. That is the name in the rail and the roster (`rail.tsx`, `agents/`) and the persona of the `kraftwerk` chat scope's system prompt (`sessions.ts`); the scope names (`general`, `kraftwerk`) and routes (`#/agents/chats`) stay as they are. Not "Chat" or "General Chats" in anything a user sees.

A workspace has a title and a slug. `name:` in kraftwerk.yml is the title, free to change; `slug:` is its address on the machine (`<slug>.localhost`, `/w/<slug>/` once one kraftwerk serves every workspace), default the folder name (`slugFromFolder`), read through `workspaceSlug()` in `src/config.ts`, stored in the registry record, `workspaceSlug` in `/api/meta`. Never derive an address from the title. A request names its workspace by slug (`src/server/target.ts`): the host form `<slug>.localhost`, the path form `/w/<slug>/…` (stripped before routing), or `ws` on a socket message; none = the server's own. One process can serve several workspaces: the hub (`startHub` in `src/server/server.ts`). `kraftwerk daemon` is a hub serving every open workspace by slug (port 1980, `KRAFTWERK_DAEMON_PORT`; each workspace's own `port:` as an alias when free), and `kraftwerk ui` hands its workspace to a running daemon (`~/.kraftwerk/daemon.json`, `findDaemon` in `core/daemon.ts`) or runs a one-workspace hub of its own (`startInspector`, the workspace as its default, reached with or without the slug). Opening a workspace in a hub gives it its own Workspace, `.env` (`core/env.ts`: everything a workspace spawns takes `workspaceEnv()`, never `process.env`), routines, git sync, cloud registration and instance file; closing it stops all of that (`stop*`/`dispose*` per workspace) and leaves the others running — anything new a workspace starts in the background needs a matching stop in `hub.close`. A closed Workspace refuses its state (`slot()` throws "workspace closed") rather than quietly recreating it, so a background loop checks `workspaceOpen()` before scheduling its next round (git sync, the cloud heartbeat), event handlers that outlive it (a dev server's exit, a detached run's exit) check before touching state, and what `hub.open` launches without awaiting catches its own errors. Open and close are serialised per hub; closing disconnects the sockets opened for that workspace, and `hub.stop()` drops every connection so an open tab cannot hold it. Background writes that outlive a call (the registry record) decide their target file when they start, not after an await. Starting and stopping a daemon's workspace goes through `hub.open`/`hub.close`, never a signal to the process. `kraftwerk daemon install` (`src/cli/daemon-login.ts`) writes a macOS LaunchAgent that runs the same node + bin with the installing shell's PATH (launchd's own would not find the agents); its test runs against a stand-in launchctl (`KRAFTWERK_LAUNCHCTL`) and a private HOME, never the real launchd. Machine-level routes (`hub.*`, `devices.*`, `protocol.get`) work without a workspace (`hub-context.ts`); anything else at a daemon's own address is a 404 asking for a slug. The client takes `workspace` (path form) and exposes `baseUrl`; the web UI finds `/w/<slug>/` in its own address (`web/src/api.ts`) and prefixes server-relative URLs from results with `withBase()` (the app preview). Links to another workspace (switcher, workspaces screen, ⌘K) go through `workspaceHref()` in `web/src/shared.tsx`, never a raw `url`: entries the answering hub serves, or a daemon would open on start, carry `slug` and `here` (`placeInHub` in `src/server/api/workspace.ts`), and are linked in the form the page was reached by — the path form stays in it, a device on the network (which cannot resolve `<slug>.localhost`) gets `/w/<slug>/`. A daemon starts and stops its own workspaces in-process (`hub.open`/`hub.close`), not through the CLI's registry path. On the default 127.0.0.1 bind every server also takes ::1 on the same port (`listen()` in server.ts): macOS resolves `<slug>.localhost` to ::1 first.

Goal-scoped folders with a brief, systems of record and links are **projects** — `projects/<slug>/project.yml` under `projects.root`, `Project*` types in `src/core/projects.ts`, `/api/projects`, chat scope `{ kind: "project", slug }`, `kraftwerk projects`. The registry of kraftwerk roots on this machine is **workspaces** — `~/.kraftwerk/workspaces`, `WorkspaceRecord`, `listWorkspaceRecords`, `/api/workspaces`, `kraftwerk workspaces` (it was `projects` until 0.48; `instances.ts` migrates the old directory once). Inside a project's `project.yml` the outside places are **systems of record** (`records:`, `SystemOfRecord`) and the slug lists are **links** (`LINK_KINDS`); a system of record is context, never a credential or a grant. The resolved kraftwerk.yml root is a workspace in code too: `resolveWorkspace()`, `ResolvedWorkspace` and `WorkspaceConfig` in `src/config.ts` (the pre-0.64 names `resolveProject`/`Project`/`ProjectConfig` stay exported as deprecated aliases for library users), `workspaceRoot()` for the current root, and `workspace*` fields in `/api/meta` (the `project*` ones there are deprecated aliases until protocol 2).

Small apps built live in a chat are **vibeables** — one folder each under `vibeables.root`, part of the workspace (synced by the workspace git, never a repository of their own). In code, config, routes and the CLI the word is `vibeables` (`VibeablesConfig`, `listVibeables`, `/api/vibeables`, `/vibeables/<slug>/` for the served files, `kraftwerk vibeables`); the singular `vibeable` names one app (`ChatMeta.vibeable`, `/api/chats/:id/vibeable`, `vibeable.yml` inside the folder). Not "repos" — a vibeable is the workspace's own work, a repository is someone else's history. A chat gets its app from the vibeables page ("open in chat") or the API (`POST /api/chats/:id/vibeable`); the chat head has no picker of its own. The attached app shows in the context column, not beside the chat: the chat owns the pane (`VibePane` with the chat id, busy state and the detach) and renders it through a portal into the column's slot (`#kw-vibe-slot`, always in the DOM), after announcing the attachment (`announceVibeable`, the `kw-vibeable` event) so the column opens the vibeables category on that app — the category shows whenever an app is attached, even for a context that links none. There is no chat split any more.

## The API is the control plane, the web UI is one of its clients

The inspector's API is meant to serve other frontends too (a native desktop or mobile app, the CLI), Paseo-style: one control plane, many clients. So routes follow one shape:

- The code is three layers: `src/core/` is the domain (agents, projects, chats with their ACP sessions, runs, git, files, …) and knows nothing about HTTP; `src/server/` is the transport (`server.ts`, the routes in `api/`, the socket, live watches, app previews in `preview.ts`); `src/client/` is the typed client. `web/` is the web UI (built to `web/dist`, which the package ships). Core never imports server: domain code that changes what a client shows calls `changed()` (`core/changes.ts`), and the server's live watches subscribe to it.
- Every endpoint is a named route in `src/server/api/<domain>.ts`: `route({ name: "projects.get", method, path: "/api/projects/:slug", summary }, async (c) => result)`. The handler **returns** its result; it does not write the response. Non-200 results are `reply(status, body)`, refusals `fail(status, message)`, and `errors:` maps a thrown domain error to a status (`statusByMessage(/^no project/)` for the usual "no x" → 404, "are off" → 409). Only streams and files are `raw: true` and write to `c.res`.
- A route that reads a JSON body declares it as a zod schema (`body: z.object({...})`): the router validates before the handler (a mismatch is a 400 naming the field), `await c.body()` returns the parsed, typed value, clients get the schema's input type for `body` (`ApiBody<N>`), and `GET /api/protocol` publishes it as JSON Schema for clients without the TypeScript types. Schemas check shape and types; meaning (slug format, cron, harness names) stays in the domain function. When a body goes straight to a domain save function, list every field it reads — `z.looseObject` keeps unknown keys but cannot take a TypeScript interface as input, so prefer a plain `z.object` with all fields when the domain reads nothing else. No manual `typeof`/`String(...)` coercion of bodies in handlers.
- Names are `<domain>.<verb>` and stable: clients address routes by name, and `ApiResult<"projects.get">` (from `api/index.ts`) is the handler's inferred return type, so the contract cannot drift from the code. `GET /api/protocol` lists every route; `test/api/protocol.test.ts` pins that list — a new route adds a line there, a removed or renamed one also bumps `PROTOCOL_VERSION`.
- Clients go through the client in `kraftwerk/src/client/` (exported as `@netnodeag/kraftwerk/client`): `api.call("projects.get", { slug })` throws the server's error, `api.request(...)` returns `{ok: true, data}` or `{ok: false, status, error, data}` (`error` is the server's message; `failure(r)` in the web UI adds the `HTTP <status>` fallback), `api.url(...)` builds links for raw routes (files, event streams). Its route table `src/client/routes.ts` is generated — after adding or changing a route run `npm run gen:client` (`test/api/client.test.ts` fails while it is stale). The web UI imports it from `web/src/api.ts` (`api`, `useApi(name, input | null, {fast, interval, refresh})` for polled data, `failure(r)` for the error text of a request); no screen calls `fetch` on `/api` or builds an `/api` URL by hand. A raw route is for bytes and streams only — a JSON view of the same data is its own typed route (`runs.fileText` next to `runs.file`).
- Live data goes over one WebSocket, `/api/ws` (`src/server/api/socket.ts`; framing in `ws.ts`, no dependency): `{id, call, input}` runs any JSON route by name, `{watch, name, input, interval}` keeps a GET route's result pushed, `{sub, topic, after}` follows `chat.<id>` / `vibeable.<slug>` events. The server evaluates each distinct watch once for all clients (`live.ts`) and pushes only changes: right after any non-GET route (the router calls `touch()`), on chat status events and new notifications, and on the slowest interval its watchers allow, for changes nobody announces. Domain code that changes what a list shows outside a route (a chat turn, a notification) calls `touch()`; streamed text does not. The browser's socket must come from our origin (`sameOrigin`, a socket is not covered by CORS). In the web UI `useApi` is a watch (`live.watch` in `src/client/live.ts`), which polls over HTTP while there is no socket, and streams go through `live.subscribe`; no screen opens an EventSource. An e2e test that stubs an `/api` route with `page.route` must also close the socket (`page.routeWebSocket("**/api/ws", (ws) => ws.close())`) so the page falls back to HTTP — see `e2e/status-line.spec.ts`.
- `server.ts` is only the HTTP transport: Host/Origin checks, static files, startup. No route logic there.
- Results are data, not presentation: no tooltip text or web-only shapes in a result a phone would also read.
- Every request has a trust (`src/server/trust.ts`): `local` (a loopback peer that addresses a loopback name and carries no X-Forwarded-*/Forwarded header — a rebinding page or a local reverse proxy also connects from loopback, so the peer alone proves nothing; inside a container or with KRAFTWERK_UI_TRUST_NETWORK=1 any peer; KRAFTWERK_UI_REQUIRE_PAIRING=1 makes nobody local), `device` (a paired device's token: `Authorization: Bearer`, the HttpOnly `kw_device` cookie a browser gets on pairing, or `?token=` on the socket) or `none`. A route is for any trusted caller by default; `access: "public"` opens it to unpaired callers (only pairing and the protocol are), `access: "local"` keeps it to this machine (managing devices). Unpaired callers get the web UI's shell (which shows the pairing screen) and 401 `{pair: true}` everywhere else, app previews included. The device store is per machine (`core/devices.ts`, `~/.kraftwerk/devices.json`, token hashes only). A watched result can depend on who asks (`devices.self`), so the socket shares watches only between callers of the same trust (and device), and a device's socket re-checks its token before each message and every 5 s (a revoked device is disconnected, close code 4401). The device store is changed only through `update()` in `core/devices.ts` (fresh read under a lock file, across the servers and the CLI). Tests that need a remote caller start the server with `startServer(fx, { trustLoopback: false })`; e2e has the same workspace served that way on the next port.
- Workspace state is never module-global. Paths come from the current workspace (`workspaceRoot()`/`getOutputDir()` in `context.ts`, backed by `currentWorkspace()` in `workspace.ts`); in-memory state a workspace owns (caches, chat sessions, dev servers, timers) is a `perWorkspace(() => …)` slot, read as `slot()`. The server runs each request in its workspace (`ws.run`), and timers, listeners and child processes started there keep it. A sweep over all workspaces (shutdown, the idle reaper) uses `slot.entries()` and `ws.run` per entry. Process-level on purpose: the instance registry (`instances.ts`), the cloud client, self-update.

The roadmap (agreed 2026-10-08), each step shipping on its own: (1) named routes + contract test — done; (2) a `Workspace` per served root instead of module globals — done (AsyncLocalStorage, so domain signatures stay as they are); then core/server/client/web layers and zod body schemas — done 2026-10-09; (3) a typed client SDK on the route names, and the web UI moves off raw `fetch`/`usePoll` onto it — done; (4) one WebSocket with calls by route name, pushed watches of any GET route and the chat/vibeable streams, replacing polling and EventSource in the UI (SSE routes kept for older clients), files staying plain HTTP — done; (5) paired devices: per-machine tokens, one-time pairing codes, `kraftwerk ui --lan`, a pairing screen in the web UI — done 2026-10-09; (6) one daemon per machine serving every workspace by slug — done 2026-10-09 (slug, requests name their workspace, `kraftwerk daemon`, the switcher and the desktop app on it); (7) an end-to-end encrypted relay via kraftwerk-cloud and a mobile app on the SDK.

## The cloud manager is a sibling repo

The kraftwerk cloud (the `~/.kraftwerk` registry over the internet: instances register and heartbeat, admins see who is active, users see their own) lives in `../kraftwerk-cloud`, its own repo with its own tests. In this repo the feature is the `cloud:` block (`CloudConfig`, `cloudFor(project)` in `src/config.ts`) and the client in `src/server/cloud.ts`, which registers after listen, heartbeats on a timer, says goodbye from the exit handlers and reports its state as `cloud` in `/api/meta`. The wire contract (register / heartbeat / goodbye bodies, the identity file under `~/.kraftwerk/cloud/`) is pinned by `test/api/cloud.test.ts` here against a fake cloud and by `test/api.test.ts` there against the real server; a change to the shape is a change to both.

## Optional features are flags in kraftwerk.yml

`git`, `repos`, `vibeables` and `projects` are opt-in blocks: absent = off, a bare key = on with defaults, `enabled: false` keeps the block but turns it off. A new optional feature follows the same shape and plumbing — `<name>RootFor(project)` in `src/config.ts` as the one reader of the block, validation next to the other blocks, a `<name>: boolean` in `/api/meta`, a toggle on the settings screen (`settings.ts` writes the block through the yaml Document API), and the UI hides every entry point while the flag is off (`useFeatures()` in `web/src/shared.tsx`).

## The harness is the security layer, not a kraftwerk allowlist

Agents run on claude, codex or pi, and those harnesses decide which tool calls need a human. Kraftwerk never overrides that judgment in either direction: it does not auto-approve a permission request (a routine that runs unattended waits for a human and declines on timeout, `src/core/chat/permissions.ts`), and it does not keep its own hand-written list of tools an agent may or may not use. Capability stays with the agent; the only kraftwerk-side choice is ruling out the harness presets that never ask (`unattendedMode` in `permissions.ts`: no claude `bypassPermissions`, no codex full access for routines) — the user's configured mode otherwise stands. "Allow always" answers are stored by the harness, so the allowed set grows from the user's real decisions. A proposed fix that would strip tools from an agent or answer on the user's behalf is the wrong shape for this repo.

## Things that happen while nobody watches go to the bell

Anything a user should notice later — a session waiting for a permission answer, a routine that finished or failed, a workflow run that ended — is one `pushNotification()` call in `src/core/notifications.ts`; the UI (bell, tab-title count, browser notification) is generic and reads `/api/notifications`. A live state (a pending permission) carries a `key` and is removed again with `dismissKey()` when it resolves, so the list never shows a question that was already answered. New outbound channels (push, webhook, desktop) hook into this module, not into the event sources.

## Every live state has a way out

Anything the UI shows as running (a run, a session, a routine) must be able to end without a trace event: the process that would write the event may never have started. A run folder that never got a trace ages by its newest file (`src/core/runs.ts`), the UI trigger records the launcher's exit code in `trigger.json` (`src/core/runner.ts`), and stop/remove work for local runs, not only sandboxed ones. Reason: a workflow that failed at launch (missing env var) sat as "running" with no button that did anything.

## Styling the inspector: Tailwind and the ui/ components

The inspector is styled with Tailwind v4 utilities on the components in `kraftwerk/web/src/ui/` (buttons: `Button`, `IconButton`; rows: `ListRow`, `PanelRow`/`PanelRows`; page parts: `Page`, `PageHeader`, `Title`, `Avatar`, `Panel`, `Section`, `Eyebrow`, `Facts`/`Fact`, `Tabs` (buttons or route links); a screen's sidebar: `SideHead`, `SideSearch`, `SideList`, `SideNote`; status: `Tag` (with `href` it links), `Badge`, `Dot`, `Kbd`; text: `Hint`, `Notice`, `EmptyState`; forms: `FormStack`, `FieldRow`, `Field`, `TextField`/`TextArea`/`Select`, `Checkbox`, `Switch`, `SwitchRow`; `Popover` — all on view at `#/ui`). Build a screen from those; reach for raw utilities only for layout around them, and never add a class-based stylesheet for a component. When two screens need the same piece, it goes into `ui/` — no local copies of a sidebar head, a checkbox row or a hint line. Besides the utilities there are four small stylesheets, each for what utilities do not express well: `tokens.css` (the design tokens), `shell.css` (where screens sit: the three columns, the screen grids, their breakpoints), `prose.css` (rendered markdown, `md-body`) and `editor.css` (the rich-text editor). `test/unit/inspector-css.test.ts` fails on a rule whose class no source file uses and on a `var(--…)` nobody defines.

Tokens: a warm paper ground (`bg-bg`), white panels (`bg-surface`) with hairlines (`border-line`), text in `text-fg` and `text-fg-2`, one `accent` for what starts something (primary button, active tab, the current row), and colour otherwise only for outcomes (`ok`, `bad`, `ask`, `live`, each with a `-soft` wash). The accent is the workspace colour: `wsPalette()` in `shared.tsx` derives the `--wsp-*` roles from kraftwerk.yml `color`, app.tsx sets them under `[data-ws-accent]`, and tokens.css re-binds `--accent`, `--accent-soft` and `--accent-container` from them; the violet is only the fallback. When a screen looks off, change a token, not a hex value in the screen. Type scale: `text-2xs` 11 … `text-2xl` 26; radii `rounded-card` (14) and `rounded-control` (9); buttons use the control radius, a pill shape is only for a status `Tag`. The interface is in the system sans, what an agent says in the reading serif (`font-reading`) — two voices, two typefaces. Shadows only under menus and dialogs (`shadow-pop`, `shadow-modal`).

`cn()` joins classes, it does not merge them: two utilities of one kind on an element (`h-9` and `h-7`) are decided by stylesheet order, not by who asked. The form controls handle that themselves (a caller's `font-mono`, `text-sm`, `h-7`, `w-auto`, `px-2` replaces the default); elsewhere don't pass a utility that fights one the component sets — add a prop instead.

Tests find things by role, label, `aria-current`/`aria-selected` and the `data-ui` hooks the components render (`data-ui="dot"` with `data-tone`, `data-ui="badge"`, `data-ui="status"`, `data-ui="decision"`), not by styling classes. A few bare hook classes stay where a test or `shell.css` needs them (`perm-card`, `session-tab`, `runs-side`, …); they carry no styles of their own.

Motion: `animate-rise` (what appears), `animate-fade`/`animate-modal` (dialogs, palette), `animate-tab-in`, `animate-slide-left`, `animate-breathe` ("working…"), `focus-flash` (the card "next" lands on), timings `--t-fast/base/slow` (120/180/260ms). Only transform and opacity animate, never layout, and `prefers-reduced-motion` stops everything; use one of these rather than inventing a duration. The composer is one box: the field inside it without a border of its own, attach and send as round icon buttons at its end, the key hints in the field's `title`.

## The inspector is one page: conversations in columns, everything else a page

The shell (`web/src/app.tsx`) has two states on one hash. A conversation route (`agents`, `team`, `chats`, `projects`, `channels` — `CHAT_ROUTES` in `shared.tsx`) shows three columns: the rail (`rail.tsx`, who can be talked to; each project's first row under it is its "🧭 Assistant", `PROJECT_ASSISTANT` in `shared.tsx`; the projects keep the workspace's order and named sections — `kraftwerk-data/projects/order.yml`, read normalised by `listProjects` as `layout`, written by `PUT /api/projects` — sorted by dragging or Alt+↑/↓ in `rail-sort.tsx`, which treats the layout as one flat token list so every move is a splice; a section's fold is per browser), the conversation, and its context (`context-panel.tsx`: what that agent, project or channel is linked to — workflows with their last run, knowledge, vibeables, repositories, agents, systems of record; the general chat shows the whole workspace). Home (`#/`) is today's dashboard in the middle column with the rail beside it (the rail's first row). Every other route is a page of the workspace under the top bar (`GlobalNav` in `workspace-tabs.tsx`: workflows, knowledge, vibeables, skills, repositories, git, workspaces, trash — expert mode only; settings and the expert switch sit beside the search in both modes; simple mode has no top navigation, the rail and the context column are the whole way around). Chat and context are one framed panel divided by a line that can be dragged (`SplitHandle` in app.tsx: the context width lands in `--ctx-w` on the shell and in localStorage `kw-ctx-w`; double-click = half and half; the `.shell.three` grid in `shell.css` clamps it), and the context's name is the space's title, a row top left above chat and context (`.space-title`, rendered by `context-panel.tsx` as a sibling of the column and placed by the `.shell.three` grid); an app opened from the rail (`?app=`) or with the strip's "full size" fills chat and context under that title (`.ctx[data-full]` hides the chat via `:has()`; "beside the chat", back, or another conversation ends it); the columns wait hidden with their state (`kw-chat-path` in sessionStorage) and come back with the next conversation link. A context row opens the thing inside the column — the page's own component (`BundleView`, `WorkflowView`, `VibePane`) wrapped in a `LocalNav` provider (`shared.tsx`): `Link` hands hrefs under that category's prefix to the provider, so the hash stays and the column re-renders at the new path; hrefs it declines (a run's page) still go to the hash. Never fork a screen for the column — embed it and give it the provider. A page embedded there is narrow: its two-column layouts go single-column, sticky side trees become static, and page-level actions the strip already offers (export, curate, the page link) are hidden — the page decides that itself, with `useEmbedded()` (true inside the `LocalNav` provider) or the `in-[.ctx-embed]:` variant on its utilities; when a new page joins the column, do the same rather than adding rules to `shell.css`. The column's last category is a browser (`context-browser.tsx`), one per context — its tabs are that conversation's reading (`sessionStorage` under `kw-browser-tabs:<context>`), kept mounted across categories and remounted when the conversation changes; `browse(url)` (the `kw-browse` event) opens a url there, and the tab that already shows that exact url comes to the front instead of a second one. Rendered markdown in the chat gets a small icon after every external link (`withBrowseIcons` + `onBrowseClick` by delegation) that opens it there. Sites that refuse embedding just show blank; the bar's window button is the way out. A screen that redirects on landing must call `navigate(to, { replace: true })`: a redirect into the conversation columns while a page is up moves only the remembered conversation path (the `kw-column-path` event); never write `location.hash` or `location.replace` from a screen. Expert mode adds pages and detail inside the same components — one UI with two depths, not two frontends (the exploratory `inspector-next/` frontend that this shell took its layout and look from was removed in 0.55.0; its ideas live here). The sessions of a conversation (a project's chats, an agent's sessions, Ralv's chats) are one component, `SessionsPane` in `sessions.tsx`: the ones you have open are tabs above the chat (remembered per context in `kw-tabs:<context>`; visiting a session opens its tab, the tab's × only closes the tab and moves to its neighbour, or to the project page / profile / new-chat pane when it was the last), and the full list is a sidebar hidden by default (`kw-sessions-list`, one setting for the whole inspector) with the delete buttons. The "new" action is a small round + right after the last tab (`NewTabButton` in `sessions.tsx`, like a browser's new-tab button); the strip's right end holds the open chat's own actions ("add coworker"), rendered there by the chat through `StripEnd` (`sessions.tsx`). A chat has no header of its own: its tab names it and the tab's dot says working or waiting; expert mode keeps one quiet line of detail (fork, harness, context and cost, model, folder) above the thread, and the account it runs as is in the composer's tooltip (a chip only when signed out). Editing the context itself (the project page, the agent profile, the channel editor, in expert mode the settings for the workspace) is the small pencil beside the space's title (`.ctx-edit`) — not a button in the chat. Those routes and the create forms (`/projects/<slug>/info`, `/agents/<slug>/info|edit`, `/channels/<slug>/edit`, `/projects|agents|channels/new`) keep their URLs but render as a modal over the conversation (`edit-modal.tsx`: `editScreenOf` picks the page, `EditModal` frames it; the shell keeps the columns on the last non-edit conversation path and closing goes back there). A screen's `/info` branch in its own column is therefore dead in the shell; the pages are exported for the modal instead. Closing the last session tab lands on the context's fresh pane (`/chat/new`), never on the edit route. The workflows page is laid out like the knowledge page (`workflows.tsx`): the workflows in a `.runs-side` sidebar (dot = last run, run count, search) and the selected workflow's view beside it (`WorkflowView`: overview with the request box and the board, details, runs); a bare `#/workflows` lands on the workflow that ran last, and the runs screen hangs off the side head, not the main navigation.

## A knowledge page is its editor

`ConceptView` in `web/src/knowledge.tsx` shows a page as a rich-text document (`DocEditor` in `editor.tsx`, MDXEditor, lazy-loaded) and saves as you type — ~1s after the last change, once more when the page is left — keeping the frontmatter untouched; the server re-stamps provenance. There is no read-only view and no `#/edit` route any more (removed 2026-09-24 with the full-screen editor). "edit markdown" is the way to the whole file as text, frontmatter included, with an explicit save. An agent's write to the file restarts the editor only while nothing local is unsaved (`lastRawRef` / `latestRef`), so nobody's typing is clobbered. Reason: Lukas wants to open a page and write, not click into an edit mode.
 The editor reports its own normalisation of the file as a change (tables, escapes), so `ConceptView` schedules a save only after the editor was touched (`touchedRef`: a pointer, key, paste or drop inside `.concept-doc`); opening a page must never rewrite it or its provenance.

## Paths are stored absolute

Any path a user hands the tool — a project root in a request body, a `kraftwerk workspaces <ref>`, `--output` — goes through `absolutePath()` in `src/config.ts` before it is stored, compared or printed in an error. It expands a leading `~` and resolves the rest; the registry under `~/.kraftwerk` never holds `~/…` or `<cwd>/~/…`. Shells expand the tilde, JSON bodies and quoted arguments do not, so `path.resolve` alone is not enough. Tilde forms are display-only (`tildify`, `rootLabel`).
